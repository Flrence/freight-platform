# Правила участия в разработке Freight Platform

## 1. Рабочий процесс

Команда использует GitHub Flow.

1. Перед началом работы обновить локальную ветку `main`.
2. Создать отдельную ветку для задачи.
3. Внести изменения и выполнить локальные проверки.
4. Создать коммит и отправить ветку на GitHub.
5. Открыть Pull Request в `main`.
6. Получить одобрение второго участника и дождаться успешного CI.
7. Объединить изменения через Squash and merge.
8. Удалить завершённую рабочую ветку.

Прямые коммиты и push в `main` запрещены.

## 2. Именование веток

Используем следующие префиксы:

- `feature/` — новая функциональность.
- `fix/` — исправление ошибки.
- `docs/` — изменение документации.
- `chore/` — инфраструктура и обслуживание.
- `ci/` — настройка автоматических проверок.

Пример: `docs/update-requirements`.

## 3. Формат коммитов

Используем Conventional Commits:

`type: краткое описание`

Основные типы:

- `feat` — новая функциональность.
- `fix` — исправление ошибки.
- `docs` — документация.
- `test` — тесты.
- `refactor` — рефакторинг.
- `chore` — вспомогательные изменения.
- `ci` — конвейер проверок.

Пример: `docs: update customer journey map`.

## 4. Pull Request

Каждый PR должен содержать:

- Описание внесённых изменений.
- Причину изменений или ссылку на задачу.
- Информацию о выполненных проверках.
- Указание на обновлённую документацию, если применимо.

Один PR должен решать одну логически завершённую задачу.

## 5. Ревью

- Каждый PR проверяет второй участник команды.
- Требуется минимум одно одобрение.
- Ревью должно содержать содержательную проверку изменений.
- Замечания необходимо исправить до слияния.
- Автор не может самостоятельно одобрить свой PR.
- При добавлении новых коммитов одобрение должно быть получено повторно, если прежнее стало недействительным.

## 6. Условия завершения

Изменение готово к объединению, если:

- Выполнены критерии готовности и завершённости из `docs/process.md`.
- Локальные проверки проходят.
- CI завершился успешно.
- PR одобрен вторым участником.
- Документация актуальна.
- При необходимости обновлён `docs/CHANGELOG.md`.

## 7. Безопасность

Запрещено добавлять в репозиторий пароли, приватные SSH-ключи, токены доступа и настоящие API-ключи.

Локальные секреты хранятся в `.env`, а пример настроек без секретных значений — в `.env.example`.

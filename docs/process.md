## Рабочая модель

Лёгкий командный процесс без формального полного Scrum. Задачи ведутся в `docs/tasks.md` (создаётся как вспомогательный файл при запуске репозитория); статусы: «Запланировано», «В работе», «На проверке», «Готово». Каждый участник может выполнять работу в обеих зонах, взаимная проверка обязательна. На модулях реализации изменения в основную ветку вносятся через PR с ревью.

## Определение готовности

Задачу можно брать в работу, когда:

- [ ] Названы пользователь или система, проблема и ожидаемый наблюдаемый результат.
- [ ] Понятна связь со сценарием из `user-story-map.md`; для задач после ЛР 2А указаны критерии приёмки.
- [ ] Для заказов и платежей описаны затрагиваемые состояния и крайние случаи (отказ, тайм-аут, повтор события).
- [ ] Для назначения водителя/авто известны необходимые сведения о массе, габаритах и времени.
- [ ] Известны зависимости (Яндекс Карты, ЮKassa, email, Android), ограничения доступа и способ проверки.
- [ ] Объём помещается в один учебный цикл либо задача разбита на более мелкие.

## Определение завершённости

Задача завершена только когда:

- [ ] Изменение оформлено PR и прошло содержательное ревью другого участника.
- [ ] Обязательные проверки CI зелёные; локально выполнены относящиеся к изменению проверки.
- [ ] Тесты по предусмотренным сценариям написаны/обновлены и проходят, включая негативные случаи, когда это важно.
- [ ] Для изменений заказов и платежей проверены переходы состояний, идемпотентность повторного события и отсутствие конфликтного назначения.
- [ ] Для изменений ролей проверено разграничение доступа заказчика, перевозчика, водителя и администратора.
- [ ] Соответствующая документация в `docs/` и пользовательское описание обновлены.
- [ ] В `docs/CHANGELOG.md` добавлена осмысленная запись.
- [ ] Изменение можно воспроизвести на чистом тестовом окружении; тестовые платежи не используют реальные деньги.

## Ритм команды

- Синхронизации **без фиксированных дней и часов, по договорённости** в общем чате; при необходимости короткий голосовой созвон.
- Перед началом учебной недели участники договариваются о следующем наборе задач и ответственном за каждую; после выполнения демонстрируют результат друг другу.
- При существенном изменении объёма, зависимости или риска команда обсуждает его отдельно и обновляет соответствующий документ.
- Для регулярного контроля даже при гибком графике каждый участник публикует короткий статус «что готово / что дальше / что мешает» перед совместной проверкой очередного этапа.

## Как принимаются решения

**Окончательное решение в собственной зоне ответственности принимает ответственный участник.** Если решение затрагивает другую зону, она предварительно уведомляется и может указать на последствия; разногласия фиксируются и обсуждаются. Существенные договорённости документируются, но формального права вето второй стороны нет. Это согласованная модель команды, а не требование Scrum.

## Инструменты

| Назначение | Инструменты |
|---|---|
| Документы | Markdown в `docs/` |
| Задачи | Вспомогательный `docs/tasks.md` со статусами, вместо отдельного таск-трекера |
| Пользовательские карты | Markdown-таблицы CJM и структурированный текст USM |
| Диаграммы | Mermaid внутри Markdown; внешний графический редактор не нужен |
| Исходники и ревью (начиная с 1Б) | GitHub, PR и CI |
| Связь | Общий чат, созвоны по договорённости |
